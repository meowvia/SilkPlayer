# SilkPlayer 商业化交付技术评估

**评估日期：** 2026-11-13  
**评估对象：** `SilkPlayer` 与 `SilkCoreKit` 两个仓库；当前检出的 `feature/v1.8.0-pro` 打磨中工作树，并参考本地已定稿的 1.6.0、各自 `main`、交付归档与发布脚本。  
**评估方式：** 静态代码、工程配置、发布链路、产品界面与随附文档审阅。本次没有运行测试或实机回归；沿用你已完成测试的结论，但不把静态审阅当作运行验证。

## 结论摘要

SilkPlayer 已有高于原型阶段的产品基础：原生 SwiftUI/AppKit 界面、独立播放核心、音视频播放和媒体库分层、SQLite 持久化、Keychain 凭据存储、网络媒体源、双语界面，以及针对播放、窗口和队列的自动化测试。当前代码体现了较多面向真实使用的故障修复和边界打磨。基于本次静态审阅，没有发现需要推翻现有架构或重做产品方向的问题；结合你已完成的测试和本地定稿状态，1.6.0 产品本体已达到交付阶段，1.8.0 则仍处于正常的预览打磨期。

**当前预览工作树还不具备直接收费发布的完整交付条件。** 主要差距不在核心播放功能，而在商用授权边界、授权/支付闭环、可复现的生产构建、公开分发签名与公证、发布资料一致性，以及当前分支修改尚未形成可审阅的发布提交。这些都可以作为明确的上线门槛逐项收口。

## 做得扎实的部分

1. **核心职责拆分清楚。** 播放器 UI 与播放核心通过 `SilkCoreKit` 接口连接，商业媒体库及音乐视图也已被集中到核心库。窗口管理、播放状态、设置和列表分别有相对明确的边界。
2. **媒体库路径考虑了真实故障。** SQLite 使用 WAL、busy timeout 与外键；扫描会保留离线 NAS 的缓存记录，并避免已删除 source 的扫描结果重新写回。扫描、过滤、缓存、增量更新的实现比简单递归遍历成熟。
3. **本地凭据处理方向合理。** SMB 凭据与签名授权收据写入 Keychain；媒体数据索引保存在 Application Support，而不是将账号密码明文塞入普通偏好设置。
4. **交互打磨不只停留在视觉层。** 窗口生命周期、快速连续启动、音乐模式窗口行为、播放器 HUD 与设置面板都已经有针对性处理。1.6.0 归档也记录了发布资产校验和及交付基线。
5. **开源依赖信息较完整。** `THIRD_PARTY.md` 列出 FFmpeg 版本、构建选项与动态库重链接说明，为后续第三方依赖审查提供了基础。

## 发布前必须解决

### P0：确认 Pro 核心的商业授权范围

`SILKCOREKIT_LICENSE.md` 标注为 Draft，授权条款授予的是个人非商业使用，并禁止未经书面授权在 SilkPlayer 内商业利用核心库（第 11–20 行）。应用拟收费、收取捐赠或用付费解锁 Pro 时，当前条款与计划冲突。与此同时，README 将核心描述为“免费供个人非商业使用”，而设置 UI 已包含 Pro 激活和购买入口。

**建议：** 在任何收费/商业公测前确定权利人、最终许可证、对外产品条款和分发范围；将核心库嵌入 SilkPlayer 的商业分发权明确写入最终许可，并与前端 LGPL、FFmpeg 动态库义务及实际分发方式一起做一次专业许可审查。同步确定 Intel/Apple Silicon 支持承诺，现有核心许可证仍只写 Apple Silicon。

### P0：把支付与授权链路做成可交付闭环

授权引擎默认购买链接为空，设置页会显示“购买页面尚未配置”；源代码还为授权接口未部署准备了专门的 404 提示。由代码能确认客户端具备签名收据验证、设备指纹和 Keychain 持久化，但不能确认生产服务端、支付、退款、密钥签发、设备解绑、客服恢复和密钥轮换已经投产。用户的授权状态恢复依赖本地收据；过期和换机等政策也需要产品化说明。

另一个值得在商用前确认的细节：解除授权会在清除本地凭据后，以收据中的掩码 key、key ID 和硬件 ID 请求服务端解绑（`SilkProLicenseEngine.swift` 第 297–319 行）。应对照服务端契约验证该字段足以识别订单、解绑失败时用户能否恢复设备名额，以及请求结果是否应反馈给用户。

**建议：** 在收费前完成端到端支付、签发、在线/离线验证、网络失败、重复激活、达到设备上限、退款/撤销、解绑和重新安装流程；公布数据处理及授权政策。购买 URL 应限定 HTTPS，而当前校验只检查 scheme 以 `http` 开头（第 125–130 行）。

### P0：为正式分发增加 Developer ID 签名与公证

`scripts/package_app.sh` 当前使用 `codesign --sign -` 做 ad-hoc 签名（第 198–213 行），没有 Developer ID、Hardened Runtime、时间戳或 notarization/stapling 流程。仓库说明也要求用户手工绕过 Gatekeeper。它适合本地开发包或技术预览，不是普通消费者下载后顺畅安装的正式交付体验，也会削弱用户对付费软件来源的信任。

**建议：** 配好 Developer ID Application、Hardened Runtime、必要的最小 entitlement、notarytool 提交与 staple 验证；在干净 macOS 用户环境验证 DMG 下载、安装、首次启动、升级与卸载。若选择暂不公证，则应明确将渠道定义为技术预览，而不是成熟收费分发。

### P1：让生产依赖可复现并由 CI 覆盖

- `SilkPlayer/Package.swift` 在非 CI 环境找不到本地核心 XCFramework 时，会回退下载 GitHub **1.1.0** 的 artifact（第 43–53 行）；当前预览核心二进制被 `.gitignore` 排除，无法从此工作树本身证明公开构建会使用与 1.8.0 API 匹配的核心。
- `ci.yml` 只在 `main` 的 push/PR 触发（第 3–7 行），而 `GITHUB_ACTIONS=true` 时 SwiftPM 用 `SilkCoreKitMock` 替代真实二进制。这样可以验证前端协议兼容和单测，但不能发现真实核心二进制缺失、接口漂移、Universal 架构缺片或生产链接失败。
- 两个仓库当前的发布材料也没有展示同一版本标签下的源代码 commit、核心源码 commit、XCFramework checksum 和 DMG checksum 的自动关联。

**建议：** 建立不可变的版本化核心产物地址和 checksum；release workflow 用真实生产 XCFramework 构建与打包，明确验证 arm64/x86_64 两个 slice，并发布构建 provenance/SBOM 或最少的 commit 与哈希清单。Mock 保留作单测目标，不要把 mock CI 结果当作生产构建证据。发布分支/合并候选需有 CI 门禁。

## 版本与维护交接事项

1. **预览工作树尚未固定是预期状态。** 当前检出的 `feature/v1.8.0-pro` 有未提交修改，两个仓库也处在不同提交进度；这与仍在打磨的预览版状态一致，不构成当前产品架构风险。合并前按计划完成更新、提交并固定两仓库的版本关系即可。
2. **版本号含 `-pro`。** `Info.plist` 的短版本与 build 都是 `1.8.0-pro`。在预览/候选版定稿时确定公开预览、候选版和正式版的版本号/build 规则；正式版 `CFBundleVersion` 应使用稳定、可递增的构建标识，授权请求上报的 app version 也应同步。
3. **发布文档需随 1.6.0 云端发布一起切换。** README 当前仍指向云端 1.5.1 资产，这是当前分发状态的正常反映；推送 1.6.0 时应同步更新下载名、打包命令和 Release 指引。另有系统要求文档仍提 macOS 12 测试包、`PROJECT_SPEC.md` 写 arm64-only 而当前脚本支持 Universal、设置页注释和历史说明的 Tab 数不一致等维护事项，应在对应版本说明中校正，避免让用户拿到包后读到旧说明。
4. **当前 Bundle ID 是 `com.silkplayer.SilkPlayer`，Keychain service 则为 `com.meowvia.silkplayer.pro`。** 若更换 Team ID、签名身份或 Bundle ID，需在签名切换和升级路径上实测 Keychain 读写、SMB 凭据继承及已购用户恢复。

## 功能与交互风险清单

### 媒体库与网络来源

- NAS/SMB/NFS 是付费版本的重要差异点，应在实际设备上覆盖服务器离线、挂载点改变、权限被撤回、凭据错误、超大目录初扫、扫描期间拔盘/移除来源、数据库升级、重复文件和用户清理磁盘空间等生命周期。
- `SilkSMBMountService` 通过 `Process` 调用 `/usr/bin/smbutil`。现有代码路径未见对进程等待设置整体超时；网络服务异常时需确认界面可取消、不会永久显示忙碌。stdout/stderr 均接 Pipe，也要确认输出量异常时不会因管道阻塞。
- 代码同时浏览 `_smb._tcp` 与 `_nfs._tcp`，但当前 `Info.plist` 的 `NSBonjourServices` 只列 `_smb._tcp`。应在目标 macOS 版本核对 NFS Bonjour 探测的权限声明与真实发现行为，并补齐配置或收窄承诺。
- 断开源、清理已删除文件、隐藏媒体与回收站操作应在 UI 中清楚区分“从库移除”和“删除磁盘文件”。涉及用户媒体的破坏性操作应提供明确确认与失败恢复提示。

### 设置和 Pro 上手体验

- 当前设置页把普通设置、局域网媒体库和授权放进同一窗口，且无购买 URL 时会落入“页面尚未配置”对话框。公测版应把未开放购买标为预览状态，避免用户误以为购买按钮失效或当前已可购买。
- 订阅/买断、设备数、退款与升级权益尚未在当前界面文案中清晰表达；这属于购买决策所需的产品信息，必须在付款前提供。
- 公开本地播放器提供 LAN 发现和网络库功能会引入用户可感知的局域网访问权限。隐私说明应解释发现目的、是否上传设备指纹/设备名/授权请求字段，并区分本地扫描与联网授权请求。

## 总体判断

你的打磨已经把产品从“能播放”推进到了完整桌面应用的层面。本次代码审阅**没有发现架构方向性问题，也没有足以否定产品交付的明显缺口**；按你补充的阶段信息，云端 1.5.1、本地定稿的 1.6.0 和仍在打磨的 1.8.0 分别处于合理的发布阶段。1.6.0 可按既定 GitHub 免费发布计划推进。1.8.0 的剩余代码更新在合并前收口即可。本文列出的 Pro 许可、支付/授权服务、签名与公证、生产构建复现事项，是正式收费分发前的商业交付配套门槛，不是要求重做播放器或阻止当前预览打磨。
